In a sentence each

  • Frontend — Next.js 15, App Router, calls the API with cookie creds. Case-conversion (snake_case ↔ camelCase) happens at the JSON boundary in src/lib/api.ts.
  • Backend — Single Go binary, stdlib router, layered as handler → service → store. Migrations run on boot.
  • Realtime — In-process realtime.Hub, fan-out via SSE. Single Cloud Run instance keeps it simple; clients refetch on event (no CRDT).
The whole product runs from one Go binary, one Next app, and one Postgres. Anything more would be vanity.

ii.

The data model.

Eight tables. Soft-deletes on calendars and participants via deleted_at IS NULL. Sessions store sha256(token) — never plaintext.

Subtleties worth knowing

  • Anonymous participants — participants.user_id can be NULL. A signed-in user can later claim a participant, linking it to their account.
  • Participant ids are public, not credentials — writes to a participant row (availability, rename, email, claim) are authorised in service.authorizeParticipantWrite: linked rows need the matching session user; anonymous rows need the secret issued once at join in the X-Participant-Token response header (only its SHA-256 lands in participants.token_hash). The frontend keeps it in localStorage["freewhen:participantTokens"] and request() sends it back. Tokens are issued only at join — an anonymous row without one (token_hash NULL) can never be written, which is why duplicating a calendar copies only signed-in participants. The owner can rename/remove anyone but cannot write others' availability.
  • Passphrase rotation — bumping access_epoch invalidates every previously-issued access token (the HMAC includes the epoch).
  • Sliding + absolute session expiry — each request advances expires_at up to 30d, but never past absolute_expires_at (created_at + 90d).

House rules

  • Folder-per-component: src/components/Foo/Foo.tsx — no barrel files.
  • API client in src/lib/api.ts auto-converts case at the JSON boundary.
  • Logging via src/lib/log.ts wrapper, never console.*.
  • Reversible actions use the Toast primitive with an Undo action — never window.confirm.

The calprovider abstraction

Recently extracted (commit 70b7641). The point: adding Microsoft, Apple, or CalDAV later is one new file plus one registry entry — zero changes to handlers or routes.

type Provider interface { Name() string // "google" OAuthConfig() *oauth2.Config // login + scopes FreeBusy(ctx, token, start, end, tz) ([]availability.TimeRange, error) AddEventURL(event) string // deep link } Registry := calprovider.NewRegistry(google) // routed via /auth/{provider}/calendar/... // and /calendars/{id}/export/{provider}

Other notable seams

  • store/ — typed methods per resource; soft-delete filtering lives here. Mocked in tests via interfaces.
  • service/ — stateless orchestration: "finalise calendar" = update DB + publish event + send emails. Also the single home for authorisation and input rules: owner-only operations take the caller's user id and go through requireOwner (→ ErrForbidden / model.ErrCalendarNotFound), participant writes through authorizeParticipantWrite, and rejected input comes back as *service.ValidationError{Code, Message}. Handlers only decode (decodeJSON), call the service, and map errors — they import service + model, never store (sentinel errors live in model/errors.go). Sign-in account resolution is service.Accounts (FindOrCreateOAuthUser / FindOrCreateByEmail). It is race-safe: CreateUser uses ON CONFLICT (email) DO NOTHING, and the loser of a concurrent first sign-in re-reads the winner's row.
  • Data integrity in store/ — availability writes lock the calendar row (FOR SHARE) and check finalised_date inside their transaction, so a concurrent finalise can't be missed. Dates are batch-inserted with unnest. A participant rename plus email change is one UPDATE.
  • realtime.Hub — in-process; fine because we cap Cloud Run instances. Replace with Redis pub/sub if we ever scale horizontally.
  • access/ — HMAC-signed tokens with embedded access_epoch so passphrase rotation invalidates everything atomically.
  • flags/ — Evaluator interface with PostHog and Noop impls. Flags are temporary per AGENTS.md — delete once rolled out. The server still builds an evaluator, but no handler reads a backend flag today (the unused Handler.WithFlags wiring was removed).
ix.

Conventions & conveniences.

Testing

  • Backend unit — go test ./... · fast · no DB.
  • Backend integration — make test-integration · embedded Postgres downloaded to ~/.embedded-postgres-go/ · integration build tag.
  • Frontend unit — vitest + happy-dom · @ alias to src/.
  • E2E — Playwright spins up embedded Postgres + Go (E2E_TEST_MODE=true) + Next.js dev server.
  • PII linting — make lint-pii blocks logger calls with email/phone/ip fields.

Environment variables

Backend
  • DATABASE_URL · PORT · CORS_ORIGIN · LOG_LEVEL
  • SECURE_COOKIES · COOKIE_DOMAIN
  • GOOGLE_CLIENT_ID / SECRET / REDIRECT_URL
  • GOOGLE_CALENDAR_REDIRECT_URL
  • RESEND_API_KEY · MAGIC_LINK_FROM_EMAIL
  • CALENDAR_ACCESS_SECRET (HMAC, ≥32B)
  • NOTIFICATIONS_HMAC_SECRET
  • POSTHOG_KEY / HOST / PERSONAL_API_KEY
  • E2E_TEST_MODE · AUTH_EMAIL_DISABLED
Frontend
  • NEXT_PUBLIC_API_URL (read once in src/lib/config.ts)
  • NEXT_PUBLIC_LOG_LEVEL
  • NEXT_PUBLIC_POSTHOG_KEY
  • NEXT_PUBLIC_POSTHOG_HOST

Repo principles

  • 12-factor config — branch on explicit vars (POSTHOG_KEY set/unset), never on NODE_ENV or a generic ENV=prod label.
  • Plans first — every piece of work has a markdown plan in plans/<category>/ with a timestamped Log.
  • Mobile first — design at 375px, enhance up.
  • Flags are temporary — delete once rolled out.
